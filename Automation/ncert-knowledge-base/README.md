# NCERT knowledge base

A shared, searchable corpus of NCERT chapter text — committed to git, built
by `../core/`'s corpus pipeline, and readable/searchable by any tool in
this repo (not just `../core/`). Fully key-free: no API calls, no
embeddings, anywhere in building or searching it.

## What's in here (committed)

- **`by-subject/<Subject>/<book-slug>__chNN.txt`** — the canonical corpus:
  cleaned, organized NCERT chapter text, one file per chapter, grouped by
  subject. This is what actually matters — read/skim these directly any time.
- **`index.json`** — a local BM25 search index built over `by-subject/`.
- **`retrieve.mjs`** — the search function (`retrieve(queryText, {subject}, topK)`)
  other tools import to query the index. No API key, no network call.

## Where this comes from

Nothing in this folder is hand-edited — it's all generated by scripts that
live in `../core/src/` (extraction → Kruti-Dev-decoding → cleanup →
indexing). See `../core/README.md` and `../core/output/ncert-corpus/README.md`
for the full build pipeline and how to add more source books. The short
version, run from `Automation/core/`:

```
node src/rebuild-corpus.mjs
```

That regenerates `by-subject/` and `index.json` here from whatever's in
`../core/input/book-library/`, then commit the result.

## Using it from another tool

```js
import { retrieve, hasCorpus } from '../ncert-knowledge-base/retrieve.mjs'; // adjust the relative depth to your caller's location

if (hasCorpus()) {
  const hits = await retrieve('algebraic identities class 8', { subject: 'Maths' }, 5);
  // hits: [{ id, subject, book, chapter, chapterTitle, text, score }, ...]
}
```

Not currently imported by anything at runtime — the API-key-based batch
generator that used to consume it (`generate-long-post.mjs`'s agentic
`search_ncert` tool) has been removed; see `../core/README.md`.
`update-factory/index.html` references this folder as a plain link in its
optional "Reference sources" prompt field — it does not call `retrieve()`
directly (browser JS can't read local files); that would require exposing
search as an actual API if it's ever needed live in the browser tools.

## Why nothing here needs an API key

`index.json` is a plain BM25 (term-frequency) index — pure local computation,
no embeddings model, no vector database, no network call at search time.
Trades some recall/semantic-matching quality for zero cost and zero external
dependency, which is the right tradeoff for a corpus this size grounding a
prompt, not powering a production search product.
